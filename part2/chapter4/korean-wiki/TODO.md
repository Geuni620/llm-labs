# 다음 챕터: NPLM 실제 학습과 평가

2026-10-20 기준. 전처리·Kiwi 토큰화·숫자 분리·빈도 집계·OOV 분석·`.npy` 정수 인코딩과 짧은 CPU/MPS 실험은 완료했습니다. 실제 전체 데이터의 2·3·5에폭 학습과 해당 Loss 비교는 아직 하지 않았습니다.

## 먼저 할 일

- [ ] **최적화한 C 코드를 실제 에폭 학습기로 연결한다.** 현재 C 실행기는 최대 4,096 update의 시간 측정용입니다. 전체 데이터 순회, 중단·재개, 가중치·Adam 상태·샘플러·누적 시간 저장, 주기적 검증과 생성 기능을 연결해야 합니다. 기존 PyTorch 학습기를 그대로 실행할 때의 속도로 C 측정값을 사용하면 안 됩니다.
- [ ] **실사용 부하에서 예산을 확인한다.** 30~60분 정도의 제한된 예비 실행에서 발열, 실제 처리량, 최대 RSS, Mac의 다른 작업 반응성을 관찰합니다. CPU 스레드 예산 4/6도 이 기준으로 선택합니다.
- [ ] **6~8시간 범위에서 실제 학습한다.** 우선 후보는 V35,328 / C8 / D64 / H128 / B512 / CPU 6스레드 / 2에폭입니다. 8시간 상한과 재개 가능한 체크포인트를 두고 실행합니다. 낮은 부하에서 약 7.42h, 앞선 높은 부하에서는 약 10.57h로 환산됐으므로 완료를 보장하는 값이 아닙니다. 실행은 다음 챕터에서 결정하며 지금 자동 시작하지 않습니다.
- [ ] **실제 Loss·PPL·생성 결과를 기록한다.** 같은 검증 타깃과 생성 조건으로 1·2에폭 및 도달한 체크포인트를 비교합니다. 공백/EOS 포함·제외 지표, 실제 타깃 예측 수, 방문 문단 수, 반복률, 실제 경과 시간을 함께 기록하고 시간–검증 Loss 곡선을 만듭니다. 3·5에폭은 추가 시간 예산을 정한 뒤 비교합니다.

## 필요에 따라 이어갈 비교

- [ ] H64 NPLM을 비교할 경우 같은 어휘·데이터와 평가 조건을 유지합니다. 약 6.02h/2에폭 환산은 모델 용량을 줄인 별도 후보이며 H128과 같은 품질이 입증된 것이 아닙니다.
- [ ] B128→B512 변경은 Adam 갱신 횟수와 학습 통계를 바꿉니다. 같은 에폭 수만 보고 품질이 같다고 판단하지 말고 검증 지표와 학습률을 확인합니다.
- [ ] CPU/MPS를 더 비교한다면 같은 배치·모델·초기화·입력 순서로 수치 검증 후 측정합니다. 최종 GPU 조합의 본 비교는 B128이고, B512 예산 후보의 CPU 시간과 직접적인 개선율을 만들지 않습니다.
- [ ] Ubuntu i5-8250U 또는 NVIDIA 비교는 접속·장치가 마련된 뒤 실제 측정합니다. 현재 해당 장치의 동일 작업 실측은 없습니다. 클라우드를 자동 대여하지 않습니다.
- [ ] 다른 체크아웃에서 재현할 때 컴파일된 실행 파일·공유 라이브러리를 새로 만들고, 경로와 소스 해시에 묶인 검증·측정 보고서를 새 출력 경로로 다시 생성합니다. 기존 결과를 덮어쓰지 않습니다.

## 보존할 조건

- 원본 Parquet, 강의 압축본, 기존 토큰·숫자 분리 결과, 사전·정수 배열과 중지된 체크포인트를 보존합니다. 큰 데이터·환경·실행 바이너리는 Git에 넣지 않습니다.
- 문서 ID 기반 train/validation/test 분리와 train-only 사전을 유지합니다. 검증·테스트 자료로 사전을 다시 만들지 않습니다.
- 기존 `training-runs/wiki-k35328/STOP`을 유지합니다. 과거 10%·25%·100% 총 14시간 비교는 보류된 계획이며 자동 재개하지 않습니다.
- Word2Vec 비교는 사용자 선택으로 중단했습니다. 현재 후속 범위는 NPLM입니다.
- 빈도/보존율로 고른 사전 크기나 단기 처리량 후보를 모델 품질의 최적값이라고 단정하지 않습니다.
