# 검토 결과: Mac NPLM 시간을 더 줄일 후보 (읽기 전용, 측정 없음)

이번 검토는 파일 편집, 컴파일, 모델 실행, 타이밍, Torch import 없이 코드와 보고서만 읽고 했습니다. 아래의 ms나 %는 기존 phase 기록과 배열 크기에서 계산한 **상한 추정**이며, 시간이 줄어든다는 보장은 아닙니다.

## 1. 같은 조건(B128/FP32/사전/AdamW/clip)에서 시도할 후보 3개

### ① CPU softmax: 4행을 동시에 처리 (bit 동일 예상)
- **위치와 방법:** `fixedwork_softmax.c`는 그대로 두고, 같은 `fw_softmax` API를 가진 새 파일 `fixedwork_softmax_ilp.c`를 만듭니다. 빌드할 때 링크 대상만 이 파일로 바꿉니다. manifest v2의 combined 명령에서 파일 하나만 다른 새 바이너리가 되며, 고정해 둔 소스는 수정하지 않습니다.
- **원리:**
  - `fw_softmax_row`(`:24-27`, `:37`)의 max 루프와 `sum += row[v]` 루프는 `-ffp-contract=off`이고 fast-math가 없어서 컴파일러가 벡터화할 수 없습니다. 그래서 한 행당 35,328개의 연산이 하나씩 앞의 결과를 기다리며 이어집니다.
  - 스레드 하나가 4행을 동시에 돌리면 각 행 안의 덧셈 순서는 그대로 두면서 서로 독립된 연산 사슬 4개가 겹쳐 실행됩니다.
  - max는 `vmaxnmq_f32`로 바꿉니다. NaN을 건너뛰는 동작이 원래 코드와 같고, max는 순서와 무관하게 결과가 정확합니다.
- **상한 추정:** FADD 지연 약 3사이클 × 35k × 32행/스레드로 계산하면 update당 약 1~1.8ms, 즉 20.3ms 중 5~9%입니다. 이 루프들이 실제로 스칼라로 컴파일됐는지는 아직 확인 전입니다. root가 `-Rpass-missed=loop-vectorize`로 먼저 확인해야 합니다.
- **회귀 검증:**
  1. softmax 모듈 2,288케이스에서 logits와 loss가 **memcmp로 완전히 같은지** 확인합니다.
  2. `check_fixedwork.py` tiny fixture를 돌립니다. B=4라 새 경로를 탑니다. irregular fixture는 B=71이라 기존 대체 경로로 빠지므로 새 경로 검증이 되지 않습니다. 남는 행 처리 경로(B%4≠0, threads>rows)도 따로 검사해야 합니다.
  3. 실제 Wiki 512 update를 돌려 `final_parameter/moment1/moment2_checksum`이 combined 바이너리와 **완전히 같은지** 확인합니다. 이게 가장 강한 판정 기준입니다.
- **root 실험:** combined와 ILP 버전을 512 update(약 10초)씩 ABBA 순서로 2블록 돌립니다. `per_update.phase_wall_seconds.softmax`의 중앙값과 wall을 비교합니다.

### ② CPU 스레드 3/4/6/8 비교 (코드 변경 없음)
- **방법:** 기존 `cpu_fixedwork_combined`에 `--threads N`만 바꿔 줍니다.
- **봐야 할 점:**
  - 고정 블록 norm, 열 블록 bias, 행 단위 softmax, 원소 단위 Adam은 이론상 스레드 수와 무관하게 같은 결과를 냅니다. Accelerate SGEMM도 같은지는 모릅니다.
  - `thread_budget()`(`fixedwork_benchmark.c:265`)이 `VECLIB_MAXIMUM_THREADS`를 실행 중에 setenv하는데, Accelerate가 이 값을 실제로 반영하는지도 확인되지 않았습니다.
  - 그래서 **checksum이 같으면 순수 속도 비교**로 볼 수 있습니다. 다르면 `check_fixedwork.py --threads 6 8`(새 report 경로로)로 허용오차 판정을 해야 합니다.
- **예상:** M1은 P코어 4 + E코어 4입니다. 8스레드는 `schedule(static)`에서 E코어 스레드가 끝날 때까지 나머지가 기다려 느려질 가능성이 있고, Mac 반응성도 나빠집니다. 다만 이건 가설입니다.
- **root 실험:** 4개 설정 × 3회 × 약 10초, 순서를 돌려가며 실행합니다. `ru_nivcsw`와 process_cpu도 함께 기록합니다.

### ③ GPU 조합: zero_none + metal_clip (+compile)
- **방법:**
  - 새 `engine_combo.py`에 CASE_OPTIONS 조합을 정의합니다. 여기서도 foreach=True, fused=False는 유지합니다.
  - 새 `verify_combo.py`는 `verify_refined.py` 방식을 그대로 따라 동결된 `verify.check_case`와 기존 허용오차를 재사용합니다.
  - 새 `run_combo.py`가 필요합니다. `run.py`는 OUTPUT/GATE 경로가 고정돼 있고 기존 파일이 있으면 실패하도록 되어 있기 때문입니다.
- **정직한 기대치:**
  - 개별 효과가 그대로 더해진다고 낙관적으로 가정하면 59.9 − 4.0 − 13.7 − 5.4 ≈ 36.8 ms/update입니다. 약 3.5k t/s, 5에폭 약 50h에 해당합니다.
  - 그래도 **C(20.3ms, 27.4h)보다 느립니다.**
  - zero_none과 compile은 둘 다 gradient 누적 경로를 건드려서 효과가 겹칠 수 있으므로 실제로는 더 작을 수 있습니다.
  - 따라서 이 실험은 GPU 경로를 정리하는 의미이고, 전체 최선 경로를 바꿀 가능성은 낮습니다.
- **root 실험:** 게이트 6개를 통과한 뒤 512 update(약 20~25초) × 3회를 돌립니다.

### 우선순위가 낮거나 보류할 것
- **CPU clip→AdamW 융합:** bit 동일하지만 clip이 활성화된 update는 66/285(23%)입니다. 활성 update당 55MB 왕복(약 1ms)을 줄이므로 평균 약 0.25ms(약 1%)이고, 측정 잡음(7~11%)보다 작습니다. dump 검사의 `optimizer_grads` 비교도 바꿔야 합니다.
- **Metal `clip_write`에서 scale==1이면 일찍 종료:** bit 동일하고, 활성 update가 102/512라 나머지 약 80% update에서 55MB pass가 빠집니다. 약 1ms/46ms(약 2%)입니다.
- **foreach AdamW + clip 배율을 하나의 Metal 커널로:** GPU에서 효과가 가장 클 수 있는 후보입니다. 다만 native fused가 m1 허용오차에서 실패한 것과 같은 종류의 위험이 있습니다. C와 같은 연산 순서를 지키고 FMA 합치기를 꺼야 합니다(`compile_shader`의 수학 모드는 확인 필요). 다음 단계로 미룹니다.
- **MPS backward(phase 진단에서 38.6%) 안에서 embedding backward 비중:** 아직 모릅니다. 실제 인덱스 패턴으로 `embedding_dense_backward`와 `index_add_`만 따로 떼어 10초 정도 재 보는 것이 진단 1순위입니다.

## 2. 학습 조건을 바꿔서 얻는 속도 (같은 조건 최적화와 별도 표로)
- **지금 바로 테스트할 가치가 있는 것: C/CPU B256과 B512.**
  - `--batch-size 512 --steps 128`처럼 예측 수를 65,536개로 똑같이 맞추면 코드 변경 없이 약 10초면 됩니다.
  - 근거: combined phase 기록(`fixedwork-cpu-comparison.json`)에서 clip + Adam + other ≈ 5.5ms가 B와 무관한 update당 고정비입니다. 나머지가 B에 비례한다고 단순 가정하면 B512는 **약 1.2배 안팎**입니다.
  - 반대로 logits가 72MB가 되어 L2를 넘으면 softmax가 오히려 느려질 수도 있습니다. 미측정입니다.
  - 참고로 MPS B512는 같은 조건의 B128 대비 1.68배였지만, 그래도 5에폭 46.3h로 C B128의 27.4h보다 느렸습니다 (`mps-cpu-comparison.txt`).
  - update 수가 1/4로 줄기 때문에 학습률(lr)과 품질은 별도로 검증해야 합니다.
- **나중으로 미룰 것:**
  - FP16/BF16: M1 CPU에는 BF16 명령이 없고, MPS FP16은 기존 판정 기준을 원래부터 통과할 수 없습니다.
  - 어휘 축소: 데이터 전처리를 다시 해야 합니다.
  - negative sampling/sampled softmax: 행렬곱과 softmax 덩어리를 직접 줄이므로 효과는 가장 클 수 있습니다. 하지만 전체 softmax 기준 validation PPL로 평가해야 해서 다음 챕터 과제입니다.

## 3. 실측 없는 Intel/NVIDIA를 정직하게 표시하는 방법
- **공식:** 시간(h) = 에폭 × 124,232,535 ÷ R(targets/s) ÷ 3600
  - 3에폭은 103,527 ÷ R, 5에폭은 172,545 ÷ R입니다.
  - 평가, 체크포인트, 데이터 적재 시간은 포함하지 않습니다.

| M1 MPS metal_clip (짧은 실측의 외삽) | 2,771.54 | 37.35h | 62.26h |

## 4. loss의 뜻과 3에폭 vs 5에폭
- **loss의 뜻:** loss는 정답 다음 토큰 확률의 평균 −ln 값입니다.
  - 시작값은 ln(35,328) ≈ **10.47**이고, 무작위로 찍는 수준입니다. MPS 기록의 첫 loss 10.47과 일치합니다 (`phase-profile-v3`).
  - PPL = e^loss입니다. 예를 들어 loss 5는 PPL 약 148로, "평균 148개 후보 중에서 고르는 정도의 불확실성"이라는 뜻입니다.
  - 낮을수록 좋지만, **학습 loss만 낮고 validation loss가 오르면 과적합**입니다.
- **3에폭 vs 5에폭:**
  - 에폭당 1.24억 개 예측에 매개변수는 690만 개라서, 5에폭 안에 과적합보다는 용량 한계(과소적합)가 먼저 올 가능성이 높아 보입니다. 이 경우 3→5에폭의 이득은 점점 작아집니다.
  - 다만 단정할 수 없습니다. 기존 실측 validation loss 데이터는 없습니다 (`training-comparison.txt`가 모두 "대기 중").
  - 장기 학습에서 `validation.ids.npy`로 에폭마다(또는 N update마다) validation loss를 기록해, 내려가는 폭이 줄거나 다시 오르는 지점을 보고 정해야 합니다. lr이 상수 0.001인 점도 수렴하는 바닥 높이에 영향을 줍니다.

## 5. SubAgents로 시간을 줄일 수 있나
SubAgent로 줄일 수 있는 건 **사람 쪽 작업 시간**입니다. 후보 코드 작성, 검증 스크립트 작성, 리뷰는 병렬로 돌리면 빨라집니다. **학습 시간이나 측정 자체는 줄지 않습니다.** 같은 Mac에서 측정을 동시에 돌리면 결과가 오염되고, 기존 실행기도 `.timing.lock`으로 직렬 실행을 강제합니다.

**추천 진행 순서:** ②(코드 변경 없음, 약 2분) → ①(새 파일 1개, checksum 동일성 판정) → CPU B256/B512(학습 조건 실험으로 별도 표) → ③.
